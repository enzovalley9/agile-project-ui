# Package trust and signing

Native connector archives currently include upstream Node.js, first-party JavaScript, platform launchers, notices, a member-hash manifest and an archive SHA-256 file. The release workflow verifies exact source, successful CI, packaged runtime and every member before publication. Those checks detect modification; a checksum downloaded from the same source is not independent publisher authentication.

**The connector distribution itself is unsigned and is not Apple-notarized.** A signature on an upstream Node binary does not sign the application, its JavaScript or its launcher. Do not disable operating-system protection globally to install it. Verify the release and follow the [installation guide](connector-setup.md), or build from reviewed source.

## Maintainer prerequisites for signed installers

Signing is an optional future distribution channel, not a requirement for the project's MIT source license. No paid account or certificate is provisioned automatically.

| Platform | Required preparation                                                                                                                                                                                                                                                 | Acceptance before claiming signed support                                                                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| macOS    | An owner-controlled Apple Developer Program membership, Developer ID identities and a notarization credential held in a protected release environment. Package the complete application/resources as an appropriate signed installer, rather than signing only Node. | Sign the installer, submit with `xcrun notarytool`, wait for acceptance, staple the ticket, verify with `pkgutil --check-signature`, `xcrun stapler validate` and Gatekeeper on a clean Mac after download.   |
| Windows  | An owner-controlled code-signing identity/service and a complete signed installer. Store signing access in a protected environment with least privilege and timestamp signatures.                                                                                    | Verify the installer with `signtool verify /pa /all`, check the expected publisher and perform a clean Windows installation/uninstall. A valid signature does not guarantee immediate SmartScreen reputation. |
| Linux    | Retain archive checksums and provenance; choose a maintained package/repository signing model before promising package-manager trust.                                                                                                                                | Verify signature identity and artifact digest independently, then install on the declared architecture in a clean environment.                                                                                |

Keep signing credentials out of source, images, logs and general pull-request jobs. Require an explicit protected release operation; never run untrusted PR code with signing secrets. Preserve already published assets: introduce signed formats under a new release and test update/rollback before promoting them.

Primary guidance: [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple Developer Program](https://developer.apple.com/programs/), and [Microsoft SignTool](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/signtool). Build provenance and signatures serve different purposes; see [releases](releases.md) and the container distribution guide.
